Choosing the benchmarks02

Two whose algorithm is in the file, not in a library

We wanted benchmarks where the hot code is the benchmark's own, so an optimization is ours rather than a library swap, and where the hotspot is one identifiable thing.

Both had to keep their output identical — byte-for-byte for pyflate, bit-for-bit for mdp. That constraint is what makes the speedups meaningful rather than a change of problem.

Method03

What the VM gave us, and what it refused

worked

  • pyperf for wall clock — 30 and 18 values per benchmark
  • perf stat for hardware counters, reproducible to under 1%
  • cProfile for exact per-function attribution
  • py-spy for the flame graphs

did not

  • perf record collects nothing for cycles: the PMU is present but its overflow interrupt never fires
  • Software events do sample — 3,845 for task-clock — but only under the system interpreter. Under the venv interpreter, which is what our capture ran, zero. We bisected the command to find that
  • But PMI in /proc/interrupts stays at 0 across a record — the overflow interrupt never fires, and sampling rides on it
  • Counting needs no interrupt, which is why perf stat is unaffected

So the flame graphs come from py-spy — the better tool here regardless, since Python 3.10 has no perf trampoline and perf could only ever have shown interpreter C frames.

pyflate · the problem07

It walked the whole table for every symbol

for x in table:                 # sorted by (length, code), up to 258 entries
    if peek(x.length) == x.code:
        return x                # and re-reads the bit buffer at each candidate

Hundreds of comparisons per symbol, 148,271 symbols, six tables. The work scales with table size — which has nothing to do with how much information a symbol carries.

But these are canonical Huffman codes: within one length the codes are consecutive integers, so an entire length collapses to two numbers.

Two benchmarks, one acceleratorAssi · Sefi07/23
pyflate · the fix08

One compare per length, not one per entry

Canonical codes of one length are consecutive integers. So a whole length needs only two numbers: limit[L], one past the last code of length L, and base[L], where that length’s symbols start in the table. If the top L bits fall below limit[L], the code ends here and the symbol is at base[L] + code.

v = peek(MAXBITS)               # read the window once
for L in 1..maxlen:             # at most 15 iterations
    code = v >> (MAXBITS - L)
    if code < limit[L]:         # does a code of this length end here?
        return symbol[base[L] + code]

Also fixed

  • bit reader: one read() for the stream, eight-byte refills
  • move-to-front: pop/insert instead of rebuilding the list
  • the final RLE pass as a single regex
  • bwt_reverse on a bytearray; local names in the hot loop

Unchanged

  • every public function and its signature
  • the output, byte for byte
  • still pure Python — no C extension, no bz2 module

Which of these earned it? We measured rather than assumed — each change reverted in turn, md5-checked, timed in the VM. Leave one out and the run costs +83.0 ms without the canonical decoder, +155.8 ms without move-to-front, +156.6 ms without the RLE regex. The change we called algorithmic is the smallest of the three. What justifies the hardware is not what the algorithm earned — it is the half of the run that is still per-symbol interpreter work after all five.

Part two11/23

The accelerator

Twenty comparators, a priority encoder, one symbol per clock — in SystemVerilog, checked against the real block.

Accelerator · datapath12

One symbol per clock, by construction

Bits arrive into a 64-bit buffer; twenty length comparators run in parallel; a priority encoder takes the shortest match; base[L] + code indexes the symbol memory; the matched length drives the barrel shifter in the same cycle, so the next symbol is ready on the next clock.

One function changes. find_next_symbol becomes a call into the driver. bzip2_main, bench_pyflake and every caller are untouched — lecture 5's first rule, do not make users change their code.

Where we stopped. The selector list — which table applies to each group of fifty symbols — is supplied by the host on TSEL rather than sequenced in hardware.

A production version puts a mod-50 counter and a small FIFO inside the block. We kept the datapath as the subject and say so, rather than implying otherwise.

Accelerator · verification14

Checked against the real block — and the test can fail

gen_vectors.py instruments the Python decoder and dumps the six real tables, the actual bit stream and every decoded (table, symbol, length). The testbench programs the tables, streams the bytes and checks each output.

148,271 / 148,271 symbols correct
        0 errors
  148,272 cycles  →  1.000 symbol/clock
  531,571 bits    →  3.59 bits/symbol

Same result inside the course VM, with its packaged Icarus Verilog 11.0 (results/rtl_sim_guest.log).

The testbench used to pass on a broken decoder. One emitting nothing but X reported zero errors, because != against an undefined value is itself undefined and if treats that as false. An unprogrammed table bank was invisible.

It now compares with !==, flags X, fails the build on a timeout, and asserts the one-symbol-per-cycle rate instead of printing it.

Mutation testing is what found all of that. Eighteen bugs injected one at a time — and against the benchmark block alone, eight passed unnoticed: deleting the end-of-input handling, tying flush low, ignoring output backpressure, building comparators only for the code lengths this input happens to use. Not a weakness of the design — a weakness of one well-formed stimulus.

So the stimulus grew: four directed streams (every code length 1–20, a stream ending on a code boundary, an unmatchable code, a corrupt table, a stream one bit short) plus a run with both handshakes throttled. Now 17 of 18 are caught. The one survivor is an unreachable guard — reported, not removed.

Why only the symbol table is SRAM. limit is compared at all twenty code lengths in the same cycle, so it needs twenty read ports — no SRAM macro has those, and it is counted above as the register file it is. The symbol table has one read port and stays SRAM: flattening it into logic too costs 49,833 cells. A direct flat lookup is worse still: the longest code is 20 bits, so a comparator-free table would need 220 entries of 14 bits per bank.

The frequency figures are inferred from the topological path length, not from static timing analysis: we have no cell library and no place-and-route, and the report says so.

Part three17/23

mdp

Value iteration over a battle state graph — where the cost turned out not to be the mathematics.

mdp · the workload18

Value iteration with bounds, over 4,823 states

while gap > tolerance:
    for each state s:
        min[s] = max over actions of  sum over successors  p * min[s']
        max[s] = max over actions of  sum over successors  p * max[s']
        freeze s when its bounds meet

The benchmark values a two-sided battle by iterating upper and lower bounds until they converge. Damage distributions are built from Fractions, so the arithmetic is exact.

Which sets the bar: preserve not just the answer but the exact sequence of floating-point additions that produced it.

mdp · baseline profile19

The cost is not the mathematics

The two tallest towers are generator expressions inside the sweep. Every successor lookup went through a dictionary keyed by a nested namedtuple, re-hashing the same keys millions of times; and getCritDist ran 3,659 times with only three distinct argument tuples, rebuilding identical distributions each time.

Two benchmarks, one acceleratorAssi · Sefi19/23
mdp · the fix20

Index the graph once, then sweep flat arrays

  • Give every state an integer index once, before the loop
  • Flatten successors, probabilities and actions into plain lists
  • Sweep over integers — no dict lookup, no tuple hashing, in the inner loop
  • Memoize getCritDist on its argument tuple
  • Write the values back into the original dictionaries at the end
result
bit-identical
not "within tolerance" — the same IEEE-754 bits

The additions happen in the original order, which is what makes that possible. Both versions are run in one process and their results compared directly: the same double, 0.8987358988699915, difference exactly zero.

Conclusions22

What we would take from this

  • Algorithm first. Both speedups came from removing work. IPC barely moved in either benchmark — the processor was never the problem.
  • Then interpreter overhead. Once the algorithm is right, what remains is the cost of being Python: a call, a bounds check, a bit-buffer update per symbol.
  • Hardware for what is bit-serial. Canonical Huffman decode is a peek, a compare tree and a shift. About 3,900 CPU cycles per symbol become one clock.
  • Not for what is memory-bound. The inverse BWT is one dependent access per byte; an accelerator would wait on memory exactly as the CPU does.
  • Measure in the environment you claim. Every number here is from the course VM, and what did not work there is in the report too.

The repository holds both reports, both scripts, the RTL and its testbench, the synthesis log and every raw measurement, with a README that reproduces all of it.

Questions23

What we expect to be asked

  • Why not just call the bz2 module? That replaces the benchmark instead of optimizing it. The brief asks us to improve the code under test.
  • Why is mdp bit-identical rather than close? We changed the indexing, not the arithmetic; the float additions happen in the same order.
  • Why not accelerate the BWT? One dependent memory access per byte. Hardware stalls on the same misses the CPU does.
  • What happens on a corrupt stream? No length matches, err latches and halts the engine. It used to livelock — the audit found that.
  • How is the table switch handled? TSEL from the host today; a selector FIFO in a production version.
  • What sets the clock? A 102-level path: twenty comparators, priority encoder, adder, symbol memory. It can be pipelined if the target demands it.
