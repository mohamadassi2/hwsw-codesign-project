Choosing the benchmarks02

Two whose algorithm is in the file, not in a library

We wanted benchmarks where the hot code is the benchmark's own, so an optimization is ours rather than a library swap, and where the hotspot is one identifiable thing.

Method03

What the VM gave us, and what it refused

Three profilers, one per layer; pyperf gives the wall clock, 30 and 18 values per benchmark.

perf record

As root on cpu-clock, in the guide’s form under python3-dbg and on the bare worker under the release interpreter. It sees the interpreter’s C frames — _PyEval_EvalFrameDefault is 39% of the baseline worker’s samples — but no Python names: CPython 3.10 has no perf trampoline.

py-spy

Reads frame objects out of process memory, so it sees the Python functions perf cannot name. The flame graphs are its; cProfile gives the exact shares.

perf stat

Hardware counters — instructions, cycles, IPC — the why. Instructions repeat to within 0.2% over three runs.

What it refused: cycles never samples here. The PMU is there (dmesg names the Haswell driver), but PMI in /proc/interrupts stays at 0 across a record; sampling rides on that interrupt, counting does not, so perf stat is unaffected. The software clock does sample — 3,645 cpu-clock samples in three seconds — so every capture uses it.

Where the time goes before we touch it

Symbol decoding and the bit reader dominate; move_to_front is the other tall tower. cProfile puts find_next_symbol at 15.2% self and 48.8% cumulative here — self is the time in its own lines, cumulative adds everything it calls, mostly the bit reads. Nearly half the run inside one function.

pyflate · the problem07

Every symbol re-reads the bit buffer, once per code length

for x in table:                 # sorted by (length, code), up to 258 entries
    if peek(x.length) == x.code:
        return x                # and re-reads the bit buffer at each candidate

The scan is bounded by table size — 147 entries here, 6.0 on average, because short codes carry most of the symbols. The cost is not the walk: it is the 2.3 snoopbits() calls per symbol around it, each a Python method call and a mask, 148,271 times over.

But these are canonical Huffman codes: within one length the codes are consecutive integers, so an entire length collapses to two numbers.

pyflate · the fix08

One compare per length, not one per entry

Canonical codes of one length are consecutive integers, so a whole length needs two numbers: limit[L] and base[L].

v = peek(MAXBITS)               # read the window once
for L in 1..maxlen:             # at most 15 iterations
    code = v >> (MAXBITS - L)
    if code < limit[L]:         # does a code of this length end here?
        return symbol[base[L] + code]

Reverting this alone costs +85.3 ms.

Also fixed

  • bit reader: one read() for the stream, eight-byte refills
  • move-to-front: pop/insert instead of rebuilding the list — +163.1 ms without it
  • the final RLE pass as a single regex — +161.8 ms without it
  • bwt_reverse on a bytearray; local names in the hot loop

Unchanged

  • every public function and its signature
  • the output, byte for byte
  • still pure Python — no C extension, no bz2 module

Which earned it? The three that can be reverted alone, each put back in turn, md5-checked, re-timed in the VM. The algorithmic change is the smallest; the two that paid most were interpreter overhead — and half the run is still interpreter work after all five, which is what justifies the hardware.

Part two10/23

mdp

Value iteration over a battle state graph — where the cost turned out not to be the mathematics.

mdp · the workload11

Value iteration with bounds, over 4,823 states

while gap > tolerance:
    for each state s:
        min[s] = max over actions of  sum over successors  p * min[s']
        max[s] = max over actions of  sum over successors  p * max[s']
        freeze s when its bounds meet

The benchmark values a two-sided battle by iterating upper and lower bounds until they converge. Damage distributions are built from Fractions, so the arithmetic is exact.

Which sets the bar: preserve not just the answer but the exact sequence of floating-point additions that produced it.

mdp · baseline profile12

The cost is not the mathematics

The two tallest towers are generator expressions inside the sweep. Every successor lookup went through a dictionary keyed by a nested namedtuple, re-hashing the same keys millions of times; and getCritDist ran 3,659 times with only three distinct argument tuples, rebuilding identical distributions each time.

mdp · the fix13

Index the graph once, then sweep flat arrays

  • Give every state an integer index once, before the loop
  • Flatten successors, probabilities and actions into plain lists
  • Sweep over integers — no dict lookup, no tuple hashing, in the inner loop
  • Memoize getCritDist on its argument tuple
  • Write the values back into the original dictionaries at the end
result
bit-identical
not "within tolerance" — the same IEEE-754 bits

The additions happen in the original order, which is what makes that possible. Both versions are run in one process and their results compared directly: the same double, 0.8987358988699915, difference exactly zero.

Part three16/23

The accelerator

Twenty comparators, a priority encoder, one symbol per clock — in SystemVerilog, checked against the real block.

Accelerator · datapath17

One symbol per clock, by construction

Bits arrive into a 64-bit buffer; twenty length comparators run in parallel; a priority encoder takes the shortest match; base[L] + code indexes the symbol memory; the matched length drives the barrel shifter in the same cycle, so the next symbol is ready on the next clock.

One function changes. decode_huffman_block calls the driver instead of its symbol loop. bzip2_main, bench_pyflake and every caller are untouched — lecture 5's first rule, do not make users change their code.

Where we stopped. The selector list — which table applies to each group of fifty symbols — is supplied by the host on TSEL rather than sequenced in hardware.

A production version puts a mod-50 counter and a small FIFO inside the block. Here the datapath is the subject; selector sequencing is the known next step.

Accelerator · verification19

Checked against the real block — and the test can fail

The golden vectors are the real block: six tables, the bit stream, and every decoded (table, symbol, length) dumped from the Python decoder.

148,271 / 148,271 symbols correct
        0 errors
  148,272 cycles  →  1.000 symbol/clock

Same inside the course VM, on its packaged Icarus 11.0.

It used to pass on a decoder emitting nothing but X.

It now compares with !==, flags X, fails the build on a timeout, and asserts the one-symbol-per-cycle rate instead of printing it.

Mutation testing found it. Twenty bugs injected one at a time — and against the benchmark block alone, twelve passed unnoticed. A weakness of one well-formed stimulus, not of the design.

So the stimulus grew — six directed streams plus three throttled runs — and now 19 of 20 are caught. The survivor is an unreachable guard: reported, not removed.

Why only the symbol table is SRAM. limit is compared at all twenty code lengths in the same cycle, so it needs twenty read ports — no SRAM macro has those, and it is counted above as the register file it is. The symbol table has one read port and stays SRAM: flattening it into logic too costs 49,804 cells. A direct flat lookup is worse still: the longest code is 20 bits, so a comparator-free table would need 220 entries of 14 bits per bank.

Frequency is inferred from topological path length, not static timing — no cell library, no place-and-route.

Conclusions22

What we would take from this

  • Algorithm first. Both speedups came from removing work. IPC barely moved in either benchmark — the processor was never the problem.
  • Then interpreter overhead. Once the algorithm is right, what remains is the cost of being Python: a call, a bounds check, a bit-buffer update per symbol.
  • Hardware for what is bit-serial. Canonical Huffman decode is a peek, a compare tree and a shift. About 4,000 CPU cycles per symbol become one clock.
  • Not for what is memory-bound. The inverse BWT is one dependent access per byte; an accelerator would wait on memory exactly as the CPU does.
  • Measure in the environment you claim. Every number here is from the course VM — including what did not work there.

The repository holds both reports, both scripts, the RTL and its testbench, the synthesis log and every raw measurement, with a README that reproduces all of it.

Questions · backup, not narrated23

What we expect to be asked

  • Why not just call the bz2 module? That replaces the benchmark instead of optimizing it. The brief asks us to improve the code under test.
  • Why is mdp bit-identical rather than close? We changed the indexing, not the arithmetic; the float additions happen in the same order. On the VM’s CPython 3.10, that is: from 3.12 sum() uses compensated summation, so there it is the original that moves, by about one ulp (mdp report, section 3).
  • Why not accelerate the BWT? One dependent memory access per byte. Hardware stalls on the same misses the CPU does.
  • What happens on a corrupt stream? No length matches, err latches and halts the engine. It used to livelock: a symbol that matched nothing consumed no bits, so the same bits came back the next cycle. err is sticky now, and the directed test hw/tb/vectors_err keeps the engine enabled for 100 more cycles and requires no further symbol and no further bit.
  • How is the table switch handled? TSEL from the host today; a selector FIFO in a production version.
  • What sets the clock? A 98-level path, tsel through the table lookups. It has to close every cycle, and it cannot simply be pipelined: the tree sits in a feedback loop, so a register inside it halves throughput. What simulation proves is throughput, not frequency.
