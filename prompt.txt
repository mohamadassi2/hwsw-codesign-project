prompt.txt - AI tools used in this project
==================================================================================
Tool: Claude (Anthropic), used as a coding/analysis assistant from the terminal,
with access to the repository, a Python environment and the course VM. All code
it produced was reviewed by us, run by us, and is covered by the correctness
checks in the repository (md5 / bit-identical result / RTL testbench). The
analysis and the decisions below are ours; the prompts are given as we typed
them, lightly trimmed.

Project setup
  - "Read the project PDF, the course lectures and tutorials, and our HW1 and
    HW2 submissions, and summarize what the project requires and what we can
    reuse."
  - "Install pyperformance locally and read the source of every benchmark on
    the approved list; tell me what each one actually does and where its time
    goes."

Choosing the benchmarks
  - "Profile all the candidate benchmarks with cProfile and give me a table:
    hotspot, how much software optimization is realistic, and whether there
    is a sensible hardware accelerator in it. Avoid anything already used as
    an example in the lectures or tutorials."
  - "We take pyflate and mdp; the accelerator goes on pyflate's Huffman
    decoder. The TA said one accelerator for one benchmark."

Optimization
  - "Write an optimized run_benchmark_opt.py for pyflate that keeps the same
    pyperf runner and produces byte-identical output. Replace the linear
    table scan in find_next_symbol with a canonical Huffman decode (the
    puff.c approach), batch the bit reader, and fix move_to_front. Do not use
    a C extension or the bz2 module."
  - "Same for mdp: keep the result bit-identical - index the states with
    integers and run the value iteration on flat lists, keep the Fraction
    arithmetic exact, memoize getCritDist."
  - "Write a local check that runs both versions and asserts the benchmark's
    own correctness gate, then profile the optimized versions so we know what
    is left."

Scripts and measurements
  - "Write script_pyflate.sh and script_mdp.sh for the course VM: environment
    setup, baseline through pyperformance, perf record + FlameGraph and
    py-spy for baseline and optimized, pyperf compare_to, perf stat. Include
    the kptr_restrict / perf_event_paranoid settings, the class is stuck on
    that."

Hardware
  - "Design the Huffman decoder in SystemVerilog: parallel compare against
    limit[L] for every code length, priority encoder, base+code index, symbol
    memory, one symbol per cycle, six table banks for the bzip2 selectors,
    and a 64-bit bit buffer with 32-bit refill."
  - "Generate golden vectors from the real benchmark block by instrumenting
    the Python decoder, and write a testbench that checks every symbol."
  - "Run a generic synthesis with yosys with the tables kept as memories and
    report cells, flops, memory bits and the longest path."
  - "Write the HW/SW interface document with a register map and the one
    software change, and draw the block diagram."

Reports
  - "Draft report_pyflate.txt and report_mdp.txt in the structure the
    assignment lists, in plain language, with the development-machine numbers
    marked as such and slots for the VM numbers."
  - "Write the README and this prompt log."

Measuring in the course VM
  - "Run both scripts inside the course QEMU/KVM guest on the assigned server
    and bring results/ back. Do not use anything measured on the laptop in
    the reports."
  - "The guest cannot reach the network - apt and pip fail. Find out why."
    (The answer was the host's systemd-resolved stub that QEMU's user-mode
    NAT forwards guest DNS to; the scripts now write the campus resolvers
    into the guest's resolv.conf.)
  - "perf record collects no samples in the guest. Do not guess: find the
    mechanism from the kernel and QEMU sources and say exactly what the
    evidence supports." (First explanation offered - 'a guest has no
    sampling PMU' - was wrong and was withdrawn; the scripts now record
    /proc/interrupts PMI counts before and after a record so the report can
    state what was measured.)
  - "The scripts' results/ directory is committed. Run the final tree from a
    clean directory in the guest, the way a grader would, and fix whatever
    breaks." (pyperf refuses to overwrite its output file; the scripts now
    clear results/<benchmark> on entry.)

Checking the optimizations
  - "Try to break the optimized pyflate: any input on which it differs from
    the original." (Found: the eight-byte refill exposed a bit-order bug in
    the copy constructor that broke every gzip stream, zero-padding at EOF
    that could loop forever, and a stale bit buffer in dropbits that
    silently corrupted FEXTRA headers. All three fixed and re-fuzzed.)
  - "Try to break the optimized mdp: prove or disprove that the value
    stream is bit-identical." (Verified over every individual state update;
    three hardening changes made, none affecting results.)

Checking the hardware
  - "Mutation-test the testbench: introduce specific bugs into the RTL and
    record which ones the test catches." (It passed on a decoder emitting X;
    comparisons are now !==, X is checked explicitly, a timeout is a
    failure, and make sim exits non-zero on failure.)
  - "Review bitreader.sv and huffman_decoder.sv for underflow, stale-state
    and livelock conditions." (Counter underflow after flush, in_ready
    computed from the pre-consume level, an unguarded memory read, and a
    non-halting error state were fixed.)

Keeping the numbers honest
  - "Write a script that fills the reports' VM section from results/ rather
    than by hand, and a second one that recomputes every derived figure in
    the reports and fails if any disagrees."
  - "Do the same for the slides."

Presentation
  - "Build the deck from the outline, following the assignment's flow, no
    code dump, with the measured VM numbers and the flame graphs." Then:
    "make it look better" - twice.

Auditing the work against itself
  Late in the project we stopped adding and started attacking what we had,
  in parallel VMs on the course server:
  - "Attack the verification chain: change one number at a time and check
    that the checkers reject the tree." Seventeen perturbations, fifteen
    caught, two through - both because a check asked whether a value appears
    anywhere in a report rather than where it is quoted. The gates now check
    by shape: every 148,xxx figure must be the symbol or the cycle count,
    every per-symbol cost must be the one recomputed from the measurement.
  - "Re-review the RTL changes we just made, looking for what we broke."
    We had rewritten the end-of-input condition to accept a host that holds
    LAST as a level; it cannot distinguish that from LAST raised before the
    final beat arrives, so one producer bubble ended the stream for good. It
    is back to the AXI form, make sim_last_level drives the level style with
    bubbles, and the testbench now fails if DONE asserts early.
  - "Check the reports against their own artifacts." Three claims did not
    survive: the per-function shares were from a profiling run that had been
    replaced (51.1%, not 49.7%), the mdp counters were quoted from the run
    the report says it does not use, and the ablation reverted move-to-front
    by patching a function the optimized decoder never calls - so it reverted
    3% of the work and reported the change as worth nothing.

  That last one is the one worth remembering. A revert that does not revert
  reads exactly like a measurement, and we believed it until it was rebuilt
  to substitute source. Measured properly, the change we had called the main
  algorithmic fix is the smallest of the three separable ones.

What we did with all of this
  Every change suggested by the assistant was read, and the ones that
  changed behaviour were run against the original before being kept: the
  benchmark outputs are compared byte for byte, the mdp values bit for bit,
  and the RTL against a golden trace of the real block. The explanations in
  the reports are ours. Where the assistant's first explanation was wrong we
  say so in the report rather than quietly replacing it - the perf sampling
  mechanism twice, the accelerator's area once, and the attribution of the
  software speedup once.
