1. Overview
----------------------------------------------------------------------------------
mdp solves a small Markov decision process: a turn-based battle between two
"Pokemon-like" fighters, where one side chooses actions and the other side's
actions and the damage rolls are random. Battle.evaluate() builds the state
graph reachable from the initial state and runs value iteration on it until
the win probability of the initial state is known to within a tolerance
(0.192 in the benchmark); the result must be 0.89873589887 +- 1e-6.

Libraries. Standard library only: collections (namedtuple, defaultdict),
fractions.Fraction for exact probabilities, and pyperf. No C extension on the
hot path.

Data structures and algorithm.
  - A state is a tuple of namedtuples: (fixed data, hp, status, stat mods,
    stats) for each side plus an "extra" field. States are used as dict keys.
  - Successor sets are computed lazily and memoized in Battle.successors:
    choice nodes list the possible actions; chance nodes carry a list of
    (next state, probability) pairs. Probabilities are computed exactly with
    Fraction (getDamages / getCritDist / _applyActionSide1) and converted to
    float when the successor list is finalized.
  - topoSort() orders all reachable states with an explicit stack.
  - Value iteration keeps a lower bound dmin and an upper bound dmax per
    state, sweeps the states in topological order updating them in place
    (choice nodes take the max over successors, chance nodes the
    probability-weighted sum), freezes states whose bounds have met, and
    stops when the bounds of the initial state are within the tolerance.

  getCritDist                           2.0%   18.4%       3,659

Reading it: about two thirds of the run is the value-iteration sweep itself
(evaluate's own body, the two generator expressions and sum/max), and about a
fifth is Fraction arithmetic while the successor graph is built. The sweep is
slow for a reason the flame graph does not show but the code does: dmin, dmax
and frozen are dictionaries keyed by the state tuples, and every update does
several lookups of a key that is a tuple of namedtuples - each lookup hashes
the whole nested structure. getSuccessors() is called from inside the sweep
for every state, twice per node (once for dmin and once for dmax), and the
generator expressions are re-created each time. The Fraction cost comes from
getCritDist being called 3,659 times with only THREE distinct argument tuples,
recomputing the same exact distributions over and over.

Hardware counters in the VM (results/mdp/perfstat_base.txt, perf stat -r 3
over four loops of the worker): the baseline retires 118,536,344,707
instructions in 48,395,707,435 cycles, an IPC of 2.45, with 24,951,795,918
branches. The IPC is healthy and the branch-miss rate is 0.54%, so this is not
a stalled or badly predicted workload - it is simply executing far more
instructions than the problem needs, which is what section 3 removes.


3. Optimizations
----------------------------------------------------------------------------------
Both changes are in benchmarks/mdp/run_benchmark_opt.py; the diff against the
shipped file is small and local.

3.1 Value iteration on integer-indexed flat lists
    After topoSort, evaluate() assigns each state a small integer once and
    builds, per state, a tuple of successor indices and (for chance nodes) a
    tuple of probabilities. The sweep then runs on plain lists: vmin[i],
    vmax[i], fz[i], with the successor indices already resolved. The sweep
    order, the in-place (Gauss-Seidel) update, the freezing rule and the
    order of the floating-point additions are exactly those of the original
    (sum() starts from 0 and adds left to right; so does our loop), so the
    converged values are the same doubles. At the end the values are written
    back into self.min / self.max / self.frozen so the object looks as it
    did before.

3.2 Memoized damage distributions
    getCritDist keeps a module-level dictionary from its argument tuple to the
    finished distribution; over a whole evaluation there are only three
    distinct tuples behind those 3,659 calls. The arithmetic is untouched and
    still exact, it is simply not repeated. The cached object is a plain dict
    rather than the defaultdict the function builds, so a later caller reading
    a missing key cannot silently extend it. Clearing the cache between
    evaluations changes neither the result nor the timing measurably (the
    saving is within one evaluation, not across benchmark iterations).

What we did not do: replacing Fraction by float in the probability math would
be faster still, but it changes the probabilities at the last bits and we
preferred a version whose result is provably identical to the original
rather than one that merely stays inside the tolerance.

Correctness. scripts/local_check.py runs both versions:
    baseline  0.8987358988699915
    optimized 0.8987358988699915        difference 0.0
    |optimized - expected| = 8.5e-15  (gate is 1e-6)

5. Hardware acceleration proposal
----------------------------------------------------------------------------------
Not applicable to this benchmark: the project's single accelerator targets
pyflate (report_pyflate.txt, hw/), following the course staff's instruction
to design one hardware component for one of the two benchmarks.

For completeness, what the profile says would be the candidate here: the
value-iteration sweep is, per chance node, a sparse dot product
sum_j p_ij * V_j followed by a compare, and per choice node a max over a few
values - a sparse matrix-vector product repeated until convergence. That maps
onto the dataflow / MAC-array pattern from lecture 5 (stream the (index,
probability) pairs of each row through a multiply-accumulate unit, read V
from a small local memory, write V back), and the graph here is small enough
(a few thousand states, a few tens of thousands of edges) to sit entirely in
on-chip memory. We did not design it; after the software fix the sweep is
~37% of a 0.4 s run, and the exact-Fraction graph construction that remains
is not a datapath problem.


6. Conclusion
----------------------------------------------------------------------------------
The benchmark's cost was not the value iteration itself but the way it was
indexed: dictionary lookups keyed by nested tuples inside the hottest loop,
plus exact-arithmetic distributions recomputed thousands of times. Indexing
the graph once and memoizing the distributions gives 3.82x in the course VM
(4.99 s to 1.31 s, 73.8% less time), and a result identical to the original to
the last bit, which is the kind of
change we would be comfortable shipping to the benchmark suite itself.
