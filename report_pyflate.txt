1. Overview
----------------------------------------------------------------------------------
pyflate is a stand-alone pure-Python decompressor for gzip (DEFLATE) and bzip2
streams, written by Paul Sladen in 2006. The pyperformance benchmark feeds it
data/interpreter.tar.bz2 (67,562 bytes) and decompresses it into 399,360 bytes,
then checks the md5 of the output (afa004a630fe072901b1d9628b960974), so any
optimization has to reproduce the output exactly.

Libraries. Only the standard library: struct (one packer), hashlib (the md5
check) and pyperf for timing. There is no C extension on the hot path; every
bit of the decoder runs in the interpreter, which is what makes it a good
subject: everything we see in the profile is Python.

Data structures.
  RBitfield        a bit reader over the file object, most significant bit
                   first, holding a Python int as the bit buffer and refilling
                   it one byte at a time with f.read(1).
  HuffmanTable     one HuffmanLength object per code (fields: code, bits,
                   symbol, reverse_symbol), kept in a list sorted by
                   (bits, code). Codes are assigned canonically by
                   populate_huffman_symbols().
  favourites       a Python list used as the move-to-front alphabet.
  buffer / out     lists of bytes objects joined at the end.
  bwt_transform    a list of ints (the "T" vector) used to invert the
                   Burrows-Wheeler transform by pointer chasing.

Algorithm for one bzip2 block (the whole benchmark input is a single block):
  1. read the block header: origin pointer, the 16x16 "used symbols" bitmap,
     the number of Huffman tables (here 6), the selector list (which table to
     use for each group of 50 symbols, MTF coded), and the code lengths of
     every table (delta coded);
  2. the main loop: decode one Huffman symbol at a time. Symbols 0 and 1
     (RUNA/RUNB) accumulate a run length of the current front symbol; any
     other symbol is a move-to-front index and the selected byte moves to the
     front of the alphabet; the table switches every 50 symbols;
  3. invert the Burrows-Wheeler transform of the resulting buffer;
  4. undo the final run-length encoding (a run of 4 equal bytes is followed by
     a count byte).
For this input, step 2 decodes 148,271 symbols from 531,571 bits, using 6
tables with code lengths between 2 and 15 bits (measured by hw/gen_vectors.py).


2. Initial analysis
----------------------------------------------------------------------------------
Tools. Two views of the same run, and one that failed. py-spy gives
Python-level frames rather than interpreter internals
(flame_pyflate_base_focus.svg), and cProfile gives exact call counts; the two
agree on which functions dominate. perf record produced nothing at all in this
guest - not with its default cycles event and not with the software events
either - and the note further down this section explains what we found when we
went looking for the reason. No perf-derived flame graph exists in results/,
which is why none is cited here.

Where the time goes (cProfile, one decode of the benchmark input, baseline).
Recomputed from results/pyflate/cprofile_base.txt by scripts/cprofile_shares.py;
shares are of bench_pyflake's cumulative time, 2.158 s under the profiler:

  decode_huffman_block          22.4%   99.0%          1
  HuffmanTable.find_next_symbol 15.4%   49.1%    148,271
  RBitfield.snoopbits           10.2%   22.4%    341,601
  move_to_front                  9.8%    9.8%     92,803
  RBitfield.readbits             9.1%   12.0%    156,708
  BitfieldBase._mask             5.8%    5.8%    655,017
  bwt_reverse                    5.5%   11.6%          1
  bwt_transform                  3.5%    4.7%          1

The flame graph puts almost the whole width under decode_huffman_block, and
inside it the widest tower is find_next_symbol with snoopbits and _mask on top
of it. That tells us where. The code tells us why:

  def find_next_symbol(self, field, reversed=True):
      for x in self.table:                       # every code in the table...
          if cached_length != x.bits:
              cached = field.snoopbits(x.bits)   # ...peek again at each new length
          if x.symbol == cached: ...             # ...and compare object attributes

It is a linear scan of the sorted code table for every one of the 148,271
symbols. bzip2 allows up to 258 entries per table; this input uses 147 (six
tables, 882 entries in total, counted by hw/gen_vectors.py and recorded in
results/rtl_sim_guest.log). A symbol therefore costs up to 147 attribute loads
and comparisons - fewer on average, because the table is sorted by code length
and short codes dominate - plus one snoopbits() call per distinct code length,
each of which calls _mask(). That is an algorithmic problem, not
an interpreter-speed problem: a canonical Huffman code can be decoded in at
most max_bits comparisons, and the table is already canonical.

Two smaller things sit underneath it: the bit reader refills one byte at a time
through the io stack (67,562 calls to f.read(1)), and move_to_front builds three
slices and a concatenation for every decoded byte. Finally the inverse BWT
(bwt_reverse, 10.0% cumulative, of which bwt_transform is 5.0%) is a loop over 400
KB doing pointer chasing through a Python list; it is memory-latency bound by
nature.

This is not a cache or branch problem: the work per decoded symbol is simply
enormous. perf stat in the VM (results/pyflate/perfstat_base.txt) gives the
cycle and instruction counts of both builds, and the instruction count is what
falls when the algorithm is fixed.

A note on profiling inside this VM, because what we found is not what we
expected and it changed which tool the flame graphs come from.

perf stat counts correctly here. The numbers in section 4.1 are real hardware
counts: 11.0 billion cycles and 28.8 billion instructions for the baseline,
IPC 2.62, reproducible to better than 1% over three runs.

perf record collects nothing for the hardware event, and for a while we thought
it collected nothing at all. Sorting out which of those is true took three
attempts and is worth writing down, because two of them were our own fault.

What we can say about the hardware event from the evidence
(results/pyflate/pmu_diagnosis.txt):
  - the guest does have a PMU. dmesg reports "Performance Events: Haswell
    events, full-width counters, Intel PMU driver", not the "PMU not available
    due to virtualization" message a guest without one prints.
  - the performance-monitoring interrupt never fires. /proc/interrupts shows
    PMI at 0 both before and after a perf record on the cycles event. Sampling
    is driven by that interrupt, so with it never arriving there is nothing to
    record - which explains the cycles event exactly.
  - counting needs no interrupt, only a counter read, which is why perf stat
    is unaffected.

The software events are a different story, and our first two probes were both
bad experiments. The first recorded against `sleep 3`, which retires almost no
instructions: no counter overflows and no samples appear even on a healthy
machine, so that probe could not tell a broken PMU from a working one. The
second, the one that chooses the event for the real capture, recorded a Python
loop a tenth of a second long - too short for a 997 Hz sampler to say much. Both
reported "no samples", and the report repeated it.

Recorded properly, over three seconds of CPU-bound Python, cpu-clock and
task-clock do sample: 5,125 and 3,604 samples, in
results/pyflate/perf_events_probe.txt. So the blanket claim was wrong.

What actually blocked the capture is narrower and we isolated it by bisecting
the command (results/pyflate/perf_isolate.txt): sampling works for the system
interpreter and not for the virtual environment's. The same `perf record -e
task-clock -F 997` gives 3,845 samples running /usr/bin/python3 and 0 running
venv/bin/python, and 11,154 with a call graph on the system interpreter. Every
capture in our scripts ran the venv interpreter, because that is where pyperf
and the benchmark's dependencies live - so every capture came back empty and
perf_event_chosen.txt records "none".

That is a limitation of how we drove perf, not of the guest. It does not change
which numbers this report quotes: perf stat, which counts rather than samples,
is unaffected, and the flame graphs come from py-spy either way.

We then recorded the benchmark itself under the system interpreter, to see what
a working capture would have given us. It gives 5,172 samples - and 509 of them
carry any interpreter frame at all, none of them a Python function name. That is
the second reason py-spy is the right tool here and not merely the available
one: CPython 3.10 has no perf trampoline (it arrived in 3.12), so perf can only
ever resolve the interpreter's own C frames, and attributing time to
find_next_symbol - which is what section 4.2 needs - is not something it can do
at all. py-spy reads the interpreter's frame objects directly and reports Python
functions by name.

So the flame graphs in results/ come from py-spy, which does not use
perf_events at all: it reads the interpreter's frame objects out of the
process's memory. That turns out to be the better tool here regardless. Python
3.10 has no perf trampoline - that arrived in 3.12 - so even a perfect perf
capture would have shown the interpreter's C frames rather than the Python
functions we needed to attribute time to. The per-function percentages quoted
below come from cProfile, which is exact.

    Two flame graphs are written per build. flame_<b>_<tag>_pyspy.svg is the
    whole process as py-spy recorded it; flame_<b>_<tag>_focus.svg re-roots the
    same samples at bench_pyflake with scripts/focus_folded.py, dropping the ten
    frames of pyperf runner above it and the ~1% of samples that never reach the
    benchmark (interpreter start-up and imports). The focused one is what the
    figures in this report and the slides show.


3. Optimizations
----------------------------------------------------------------------------------
Everything below is in benchmarks/pyflate/run_benchmark_opt.py and shows up as
a plain diff against the shipped file. The algorithm, the classes and the
public behaviour are unchanged; the output is byte-identical.

3.1 Canonical Huffman decode instead of a table scan
    HuffmanTable now builds, once per table, the same three arrays zlib's
    puff.c uses: for each code length L, limit[L] = first_code[L] + count[L]
    and base[L] = index[L] - first_code[L], plus the symbol list in table
    order. Decoding one symbol is:
        v = field.snoopbits(max_bits)          # one peek
        for L in range(min_bits, max_bits+1):  # at most 15 iterations here
            code = v >> (max_bits - L)
            if code < limit[L]:
                field.readbits(L)
                return syms[base[L] + code]
    The canonical property (codes of length L form one consecutive range,
    and any prefix that is not a shorter code is >= first_code[L]) makes the
    single comparison sufficient. This replaces a scan of up to 147 object
    compares, and several snoopbits() calls per symbol, with one peek and a
    handful of int operations.

3.2 Bit reader
    The input is read once (f.read()) and the buffer is refilled 8 bytes at a
    time with int.from_bytes instead of one byte per f.read(1). Masks come
    from a precomputed list instead of a method call; readbits() masks the
    buffer to the remaining bits instead of building ~(mask << bits).

3.3 Move-to-front
    l.insert(0, l.pop(c)) - two C-level list operations instead of three
    slices and a concatenation. Same result.

3.4 Final RLE pass
    A compiled regular expression (.)\1\1\1(.) with a replacement function
    walks the buffer left to right exactly as the original byte loop did, but
    the scan runs in C.

3.5 Local names in the main loop and a bytearray in bwt_reverse.

What we deliberately did not do.
  - No C extension, numpy, or the stdlib bz2 module: that would replace the
    benchmark rather than optimize it, and the point of pyflate in
    pyperformance is to exercise the interpreter.
  - No caching across benchmark iterations.
  - We did not push the Huffman decoder further (a 2^max_bits direct lookup
    table would remove the loop entirely). The remaining Huffman share is
    exactly the part we propose to move into hardware in section 5, so we
    stop the software at the point where the algorithm is right and what is
    left is bit-level work.

3.6 Which of those five actually earned the speedup
    Quoting one overall ratio for five changes says nothing about which of them
    mattered, and we assumed the algorithmic one dominated. It does not.
    scripts/ablation.py reverts one change at a time to the shipped
    implementation and times the result; every variant is checked against the
    benchmark's own md5 before it is timed, so a variant that decoded wrongly
    could not appear. Measured in the VM (results/pyflate/ablation.txt):

        baseline                                     1,111.5 ms   1.00x
        optimized (all of 3.1-3.5)                     480.8 ms   2.31x
        optimized, 3.1 reverted to the table scan      563.9 ms   1.97x
        optimized, 3.3 reverted to the slice rebuild   636.7 ms   1.75x
        optimized, 3.4 reverted to the per-byte loop   637.4 ms   1.74x

    Leave one out and the run costs 83.0 ms more without the canonical decoder,
    155.8 ms more without the move-to-front change, and 156.6 ms more without
    the RLE regex - against a largest run-to-run spread of 69.9 ms, so the
    ordering of the last two is not resolved and we do not claim one. These are leave-one-out differences, not a decomposition:
    they do not multiply out to 2.32x, and each says only what the run costs
    with that one change put back. 3.2 (the bit reader) and 3.5 (local names,
    the bytearray) are woven through the decode loop and cannot be reverted on
    their own, so what they are worth is whatever these rows do not explain.

    Two things in that table are worth saying out loud. The first is that the
    change we called algorithmic is the smallest of the three, and the two
    largest are the ones that look like housekeeping - replacing a list rebuild
    with a pop and an insert, and replacing a per-byte loop with one regex. The
    second is that we nearly did not measure the RLE pass at all: an earlier
    version of this script reverted move-to-front by patching the module-level
    function, which the optimized decoder does not call because it inlines the
    pop and insert into the decode loop. That version reverted 2,966 of 92,803
    operations and reported the change as worth about nothing, and we believed
    it until the ablation was rebuilt to substitute source instead. A revert
    that does not revert is worse than no measurement, because it reads like one.

    What that means for section 5 is not what it first appears. The case for
    hardware is not that the algorithm was slow - it was not, and on this input
    the scan is only six entries long. It is that after all five changes, about
    half the run is still per-symbol interpreter work: a method call, a short
    loop and two bit-buffer updates, 1,644 ns per symbol. The ablation sharpens
    that argument rather than weakening it, because what paid best in software
    was removing per-operation interpreter overhead, and that overhead is
    exactly what a one-symbol-per-clock datapath does not pay.

    The same script also explains why the scan is not as expensive as it looks.
    results/pyflate/table_stats.txt instruments the shipped decoder on this
    input: the largest table has 147 entries, not the 258 bzip2 permits, and
    the scan touches 6.0 entries per symbol on average because the table is
    sorted by code length and the short codes carry most of the symbols. What
    the canonical decoder removes is the repeated bit peeking around it -
    341,601 snoopbits() calls for 148,271 symbols, 2.3 per symbol, each one a
    method call and a mask - which is exactly the call count cProfile reports.


Correctness. scripts/local_check.py decompresses the input with both versions
and compares the bytes: identical (399,360 bytes, md5
afa004a630fe072901b1d9628b960974), and the same comparison is repeated on
eight further bzip2 streams built on the spot - empty, one byte, 70 KB of a
single byte, and a multi-block payload, at compression levels 1 and 9 - so the
equivalence rests on more than the one input the benchmark ships. The md5 check
inside bench_pyflake() also passes in every run.

                                self     cum      calls
  find_next_symbol              28.5%   51.1%    148,271

  readbits                      12.0%   12.1%    156,708

    Symbol decoding plus bit extraction is still about half the run even with
    the right algorithm, because each symbol still costs a Python method call, a
    loop of a few iterations and two bit-buffer updates. That is
    find_next_symbol's 51.1% cumulative share, which already contains snoopbits
    and the readbits calls made under it; adding those rows to it again would
    count the same work twice. The inverse BWT is 18.2% - bwt_reverse's
    cumulative share, which likewise already contains bwt_transform's 11.3% -
    and it is a pointer chase through 400 KB. The first part is what hardware
    is good at; the second part is not.

    One caveat on all of these shares. cProfile's call counts are exact, but its
    time shares are not: it charges a fixed cost per call, so functions called
    hundreds of thousands of times carry profiler overhead that the one-call
    frames do not. _mask's 655,017 calls are the clearest case. That biases the
    shares against decode_huffman_block and towards the small hot functions, so
    the 51.1% below is if anything an understatement of what the accelerator
    replaces. The py-spy flame graphs, which sample rather than instrument, put
    find_next_symbol at 52.6% and agree on the ordering.


4.3 Reproducibility
    Three independent runs of these scripts in the same guest are kept, each
    made by extracting the tree into an empty directory and running them the
    way a grader would. The shipped set is one of them; the other two are under
    results/reproducibility/ (the second run) and results/reproducibility/run3/
    (a full end-to-end run of the submission as it now stands).

        run          pyflate            mdp
        shipped      2.365x (477.2 ms)  3.834x (1.303 s)
        second       2.385x (473.0 ms)  3.820x (1.305 s)
        third        2.316x (483.9 ms)  3.822x (1.308 s)

    So mdp's ratio is stable to 0.4% across the three, and pyflate's spreads by
    3.0% - 2.32x to 2.39x. That is larger than we first claimed from two runs,
    and it is the honest figure: pyperf's own standard deviation on the
    optimized pyflate run is about 0.9%, so a 3% spread across separate boots
    of the guest is a few sigma, not noise we can wave away. Nothing in the
    argument turns on the third decimal - the claim is a factor of about 2.4 on
    pyflate and about 3.8 on mdp, and all three runs support both - but a
    report that says "stable to well inside 1%" on two runs and is then handed
    a third at 3% has learned something about how many runs it takes.
    scripts/compare_runs.py compares any two of them.

    A fourth run is deliberately excluded, and the reason is the point of the
    contention check. It reported mdp at 2.33 s against 1.30 s while executing
    the same 31.4 billion instructions: the shared host was busy and "CPUs
    utilized" had fallen from 1.00 to 0.58, so the wall clock measured the
    host's load rather than this code. Both scripts now read that figure from
    perf, print a warning below 0.95 and record it in
    results/<benchmark>/contention.txt - 0.994 to 1.003 across the runs that
    are shipped. It is the one measurement error that would have been invisible
    in the numbers themselves.

5. Hardware acceleration proposal
----------------------------------------------------------------------------------
5.1 What we accelerate
    A canonical-Huffman symbol decoder for the bzip2 path: the hardware form
    of the loop in 3.1. Software keeps parsing the block header and building
    the per-table limit/base/symbol arrays (once per 900 KB block, negligible),
    writes them into the accelerator, streams the compressed bytes in and gets
    a stream of 9-bit symbols back. Move-to-front, the run expansion, the
    inverse BWT and the final RLE stay in software and run unchanged over the
    symbol buffer.

5.2 Why this component
    - It is the largest remaining share after the software fix (51.1%).
    - It is bit-serial work: peek some bits, compare against a few limits,
      add, look up. A CPU spends hundreds of instructions per symbol doing
      that through the interpreter; hardware does the compares in parallel
      and needs one clock per symbol.
    - Its state is tiny and block-local (six small tables), so the interface
      is "tables in, bytes in, symbols out" with nothing shared with the CPU
      during the run.
    - The other big piece, the inverse BWT, gains nothing from a datapath: it
      is one dependent memory access per output byte. Lecture 4's point that
      "it's always the memory" applies to it, not to Huffman decoding.

5.3 Inputs and outputs
    signal            width   direction  meaning
    in_data           32 b    in         compressed stream, MSB first; in_valid/in_ready handshake
    in_last           1 b     in         end of stream; missing bits then read as zero (as in software)
    tbl_we, tbl_sel,          in         table programming: bank 0..5, kind (length row / symbol
    tbl_kind, tbl_len,                   entry), L = 1..20, limit[L] (21 b), base[L] (22 b signed),
    tbl_limit, tbl_base,                 symbol index (9 b), symbol (9 b)
    tbl_idx, tbl_sym
    tsel              3 b     in         active table for the next symbol (bzip2 selector)
    run               1 b     in         decode while high
    sym               9 b     out        decoded symbol, sym_valid one cycle after the bits were consumed
    len               5 b     (internal) code length consumed this cycle, 1..20
    err               1 b     out        no code length matched (corrupt stream)
    Operating frequency: see 5.7; we design for one symbol per clock at
    ~200 MHz on an FPGA and ~400 MHz on an ASIC process.

5.4 Architecture (hw/rtl/, see the block diagram)
    bitreader.sv        64-bit left-aligned bit buffer. Presents the next 20
                        bits (peek) every cycle; the decoder answers with len
                        and the buffer barrel-shifts len bits out in the same
                        cycle; refills 32 bits per cycle when there is room.
                        After the last word it pads with zeros, like the
                        software reader at EOF.
    huffman_decoder.sv  For every code length L = 1..20 at the same time:
                        code_L = peek >> (20 - L); hit_L = code_L < limit[tsel][L].
                        A priority encoder picks the smallest L with a hit; that
                        is len, combinational, fed straight back to the bit
                        reader. idx = base[tsel][len] + code_len goes to the
                        symbol memory and the symbol comes out one clock later.
                        Six banks of limit/base rows (21 x 43 bits, lengths 0..20) and six
                        symbol memories (258 x 9 bits), written by software.
    huffman_accel_top.sv the two glued behind the register/stream interface.
    Control is minimal: run, tsel, and the table write port. Throughput is one
    symbol per clock as long as peek_valid holds, which with 32-bit refills and
    codes of at most 20 bits is always.

    Verification. hw/gen_vectors.py runs the optimized Python decoder on the
    benchmark input with find_next_symbol instrumented and writes out the six
    real tables, the compressed bit stream from the first symbol onward, and
    every decoded (table, symbol, length). hw/tb/tb_huffman.sv programs the
    tables, streams the bytes and checks each output. Result (Icarus Verilog,
    `make sim` in hw/):
        148,271 / 148,271 symbols correct, 0 errors
        148,272 cycles  ->  1.000 symbols per cycle
        531,571 bits consumed, 3.59 bits per symbol on average
    The same block also decodes correctly with the input and output handshakes
    gated pseudo-randomly (`make sim_bp`): all 148,271 symbols, 0 errors, at
    0.500 symbols per cycle, which is the throttle working rather than a
    defect.
    The same testbench also passes inside the course VM, with the Icarus
    Verilog 11.0 that Ubuntu 22.04 packages (results/rtl_sim_guest.log:
    148,271 symbols, 148,272 cycles, 0 errors). Getting it to run there took
    three changes to the testbench and none to the RTL - that simulator
    rejects a string as $fgets's target, and aborts internally on an always @*
    block that reads a large array with a variable index and on a ?: over int
    variables in a continuous assignment - so the stimulus is written as plain
    Verilog-2001 processes with explicit sensitivity lists.
    The decoder therefore reproduces the software's decode of the whole
    benchmark block, symbol for symbol. There are no stall cycles in that
    figure - 148,271 decodes plus one pipeline-drain cycle - because the bit
    reader accepts a refill in the same cycle the decoder consumes, so the
    buffer never runs dry even at the longest codes.

    What the cycle count does not include: programming the six tables costs a
    further ~1,000 write cycles per bzip2 block, which the host does once
    before streaming the block; and the selector list, which says
    which of the six tables applies to each group of 50 symbols, is supplied
    by the host on the tsel input rather than sequenced in hardware. A
    production version would put a mod-50 counter and a small selector FIFO
    inside the accelerator so the host writes the list once per block instead
    of tracking it per symbol; we left it out to keep the datapath the subject
    of the design, and section 5.7 counts the cost.

    The testbench has properties that matter, because a self-checking
    testbench that cannot fail is worth nothing. It compares with !== and flags
    any X, so a decoder that emits undefined values - what an unprogrammed
    table bank produces - is caught rather than silently passing (with ==, a
    comparison against X evaluates to X, which `if` treats as false). The
    watchdog counts as a failure and exits non-zero, so a decoder that stalls
    fails the build instead of ending quietly. The one symbol per cycle is
    asserted, not merely printed. The bits consumed are accumulated from the
    decoder's own len output rather than from the golden file, so a decoder
    that consumed nothing could not print the right total. And a symbol offered
    while the consumer is not ready must still be there, unchanged, on the next
    cycle.

    All of that came from mutation testing, and most of it used to be absent.
    hw/tb/mutate.sh injects one bug at a time into the RTL and runs the whole
    simulation suite for each; hw/tb/MUTATIONS.md records every outcome.
    The important result is not the score but what the score exposed. Against
    the benchmark block alone - one well-formed bzip2 block - twelve of the
    twenty mutations passed unnoticed, including deleting the end-of-input
    handling, tying the flush signal low, ignoring output backpressure, and
    building comparators for only the code lengths this input happens to use
    (2..15 of the 20 the format allows). None of those is a weakness of the
    design; all of them are a weakness of a single well-formed stimulus, which
    never runs out of input mid-code, never presents a code that matches
    nothing, never stalls the consumer and never uses the extreme code lengths.

    So the stimulus was extended rather than the score explained away.
    hw/tb/gen_synth_vectors.py builds six small directed streams - every code
    length 1..20 including the all-ones maximum code; a stream that ends
    exactly on a code boundary; an incomplete code, so that some bit pattern
    matches nothing; a table whose base row points past the symbol table; a
    stream that ends one bit short of the shortest code; and one that is a
    whole number of 32-bit words, so the buffer drains to zero and `done` can
    be observed at all. `make sim_bp` reruns the real block with both
    handshakes gated pseudo-randomly, `make sim_last_level` presents LAST as a
    level with producer bubbles, and the draining stream is run again with the
    producer stalled for 40 cycles before it hands over the final word.
    `make sim_all` runs all ten.

    Against that suite 19 of the 20 mutations are caught. The one survivor is
    reported rather than removed: the bit reader's saturating bit-count guard
    is unreachable, because the decoder now refuses to consume more bits than
    the buffer holds, so nothing can drive the counter below zero. Unreachable
    code cannot be killed by any test, and deleting the guard to improve the
    score would be the wrong trade - it costs nothing and protects the reader's
    interface against a consumer that does not make the same promise.

5.5 Hardware/software interface (docs/hw_sw_interface.md has the full map)
    Memory-mapped registers: CTRL (run / reset / last), STATUS (busy, error,
    buffer level), TSEL, TBL_ADDR + TBL_DATA for table programming, DMA source
    and destination for the byte stream in and the symbol stream out, and a
    symbol counter. Per block the host writes at most 6 x (20 + 258) table
    entries, points the DMA at the compressed bytes and at a symbol buffer,
    sets RUN, and either writes TSEL every 50 symbols or (better, and what the
    RTL's tsel input is shaped for) hands the selector list to a small SRAM
    and a counter in the accelerator.
    On the software side exactly one function changes, decode_huffman_block:
    after the tables are built it calls the accelerator instead of the symbol
    loop and then runs the unchanged MTF / BWT / RLE code over the returned
    symbols. bzip2_main(), bench_pyflake() and every caller are untouched -
    lecture 5's first rule, do not make users change their code.

5.6 Expected performance (with the assumptions spelled out)
    What the accelerator replaces is find_next_symbol and the bit reads it
    makes. In the optimized profile (section 4.2) find_next_symbol is 28.5% of
    the run by itself and 51.1% cumulatively, and the difference between those
    two - 22.6% - is almost exactly snoopbits (11.2%) plus readbits (12.1%).
    snoopbits is called from nowhere else (148,271 calls, one per symbol);
    readbits is called 156,708 times against 148,271 symbols, so all but 8,437
    of its calls are made under find_next_symbol and the rest is block-header
    parsing.
    So the cumulative figure already contains the bit extraction: the share to
    use is 51.1%, and adding snoopbits and readbits to it would count the same
    work twice. (An earlier draft of this report did exactly that and quoted
    ~62%; the number below is the corrected one.)

    Take the optimized run measured in the VM, 477 ms, of which that part is
    51.1% = ~244 ms. In the accelerator the same work is 148,272 cycles:
        at 200 MHz   0.74 ms
        at 400 MHz   0.37 ms
    Add data movement: 66 KB in and 148,271 x 2 bytes out over PCIe or an AXI
    DMA is well under 0.1 ms, and the ~1,000 table-write cycles over MMIO are a
    few microseconds. Allow ~0.6 ms for DMA setup and the MMIO round trips, so
    the accelerated part is ~1.3 ms in total. The run becomes
        477 - 244 + 1.3  =  ~235 ms     ->  ~2.0x over the optimized software,
                                          ~4.8x over the shipped benchmark.
    Per symbol the software spends 244 ms / 148,271 = ~1,644 ns, about 3,900
    cycles at 2.4 GHz, against one cycle in hardware - three orders of
    magnitude on the accelerated part alone. The whole-program gain is bounded
    by Amdahl's law: the inverse BWT and the Python glue around the symbol
    stream stay where they are, and they are what the remaining 235 ms is.

    One assumption in that arithmetic is worth pricing rather than hiding. In
    this version the host drives tsel, so it writes the selector register once
    per 50 symbols: 148,271 / 50 = 2,966 MMIO writes per block. At roughly a
    microsecond each that is about 3 ms - more than the decode itself - which
    would move the projection from ~235 ms to ~238 ms and the ratio from 2.0x
    to about 1.95x. It is why docs/hw_sw_interface.md lists the selector SRAM
    as the better design: 18,002 entries of 3 bits is about 7 KB and takes the
    host out of the symbol-rate loop entirely.

    Assumptions, stated so they can be argued with: the host-side loop that
    consumes the symbol buffer (move-to-front, the appends) costs what it costs
    today; DMA and MMIO latencies as above; no overlap between CPU and
    accelerator, so the accelerator's own time is added rather than hidden -
    with overlap it disappears entirely and the bound becomes 477 - 244 = 233
    ms. The selector list is assumed already in the accelerator (section 5.5
    explains that it is not, in this version, and what that would cost).

5.7 Performance / area / power trade-offs
    Area (docs/synthesis_yosys.txt, generic 2-input gates).
    Which figure to quote depends on what the tables really are. limit_r is read at all twenty code lengths in the
    same cycle - that parallel compare is the design - and base_r is read
    asynchronously. No SRAM macro has twenty read ports, so those two are
    register files and have to be counted as flip-flops. Only the symbol
    table, one synchronous read port, is an SRAM candidate. Counting them that
    way:
        18,796 cells: 5,441 flip-flops, 13,352 gates, and one memory of
        13,932 bits (~13.9 kbit, 1.7 KB) for the symbol table. The register
        files are 6 x 21 x 21 = 2,646 bits of limit and 6 x 21 x 22 = 2,772
        bits of base, which is most of those flip-flops.
    An earlier draft quoted 2,768 cells and 74 flip-flops. That is what the
    same flow reports when all three tables are left as memory cells, because
    `stat` does not charge for a memory - and it silently assumed the
    twenty-read-port SRAM that cannot be built. The figure above is the honest
    one and it is what this report uses.
    The logic itself is a 64-bit barrel shifter, twenty 21-bit comparators, a
    20-to-5 priority encoder and one 22-bit adder; the rest is table storage
    and its read muxes. Flattening even the symbol table into logic gives
    49,804 cells (the second run in docs/synthesis_yosys.txt), so keeping that
    one table as SRAM is worth about 31,000 cells.
    Frequency: the longest combinational path is 98 gate levels, and Yosys
    reports it ending at the sticky error flag - a status bit the host reads
    once per block, not per symbol. What has to close at the symbol rate is
    peek -> the parallel compare -> the priority encoder -> the bit-buffer
    shift, which is shorter. We did not run FPGA or ASIC timing, so any
    frequency here is an estimate. Section 5.6 does use it, so it is worth
    saying how little turns on it: the decode is 148,272 cycles, which is
    0.74 ms at 200 MHz and 0.37 ms at 400 MHz, against a 477 ms run. Halving
    the clock moves the projected run by less than a millisecond and leaves
    the ratio at 2.0x. What the simulation establishes is throughput, not
    frequency: one symbol per cycle for all 148,271 symbols. The 200 MHz
    figure assumes the compare tree split into two pipeline stages (~50 extra
    flops, one more cycle of latency, throughput unchanged), which is not in
    the RTL as it stands.
    Power: we have no cell library, so there is no absolute power number to
    give and the assignment does not ask us to synthesize to one. What can be
    said is the activity per symbol on each side. The accelerator clocks ~5.4k
    flip-flops and toggles one 64-bit shift, twenty 21-bit comparators, a
    20-to-5 priority encoder, one 22-bit add and a single read of a 13.9 kbit
    SRAM - one clock, 5 ns at 200 MHz. The CPU spends ~3,900 cycles of a 2.4 GHz
    Haswell core on the same symbol, about 1.6 us. Taking a core under load at
    the usual 5-15 W and being generous to the accelerator at 50 mW, that is
    roughly 10-25 uJ per symbol against roughly 0.25 nJ: four to five orders of
    magnitude, and the conclusion survives an order of magnitude of error in
    either assumption. The practical cost is not the datapath but the DMA
    traffic, which is bounded by the input size: 66 KB in and 290 KB of symbols
    out per block.
    Alternatives we considered:
      - a direct 2^max_bits lookup table (one memory read per symbol, no
        compare tree): fastest, but 2^20 x 14 bits per table and six tables
        per block, reloaded every block - the memory dominates everything;
      - a bit-serial FSM (one bit per cycle, walking the canonical counts):
        a few hundred gates, but 3.6 cycles per symbol on average and 15 in
        the worst case;
      - our parallel-compare design sits between the two: one symbol per
        cycle with ~13k gates, ~5.4k flops of table registers and 13.9 kbit
        of symbol SRAM;
      - moving move-to-front into the accelerator too (a 256-entry shift
        register) is the natural next step and would take another ~5% of the
        software time off; the inverse BWT is not worth moving.


6. Conclusion
----------------------------------------------------------------------------------
The shipped benchmark is slow in the ordinary way a pure-Python decoder is slow: a
linear scan of the code table for every symbol, a bit reader that refills one byte
at a time through the io stack, a move-to-front that rebuilds a list, and a final
run-length pass that walks the output byte by byte. Replacing all four in pure
Python gives 2.37x in the course VM (1.13 s to 477 ms, 57.7% less time), with
output identical to the original byte for byte, and the ablation in section 3.6
says no single one of them dominates.

What is left is different in kind. About half of it is per-symbol bit work -
find_next_symbol and the bit reads under it - which is what a small datapath does
in one clock, and about a quarter is a pointer-chasing inverse BWT, which is
memory-bound and stays on the CPU. The proposed accelerator is ~13k gates plus
5.4k flip-flops of table registers and 13.9 kbit of symbol SRAM. It decodes the
whole benchmark block at one symbol per cycle in simulation with zero errors,
changes one function in the software, and brings the run to roughly 2.0x over our
optimized code and ~4.8x over the original - at which point the inverse BWT is the
largest single item left, and the next gain would have to come from somewhere
other than the decoder.
